FIGURAS UML — módulo RabbitMQ (Atividade 01 U1) — Atualizado: 30/09/2026
Fonte PlantUML (.puml) nesta pasta; PNG renderizado em uml/png/.
Duas famílias: 01-05 descrevem o SISTEMA (implantação, componentes, sequência,
classes). 06-11 descrevem a IMPLEMENTAÇÃO, um recorte por padrão GoF, na mesma
ordem da pasta src/ (categorias GoF).

--- SISTEMA ---------------------------------------------------------------

01 implantacao containers.puml  -> png/01 implantacao containers.png
   DIAGRAMA DE IMPLANTAÇÃO: host Docker, rede interna do compose, os 6 serviços
   (cliente1/2, conversor1/2, storage1/2), as 4 pastas montadas (ro/rw) e a caixa
   rabbitmq com fila.originais, exchange convertidas (fanout), fila storage.1 e
   fila storage.2.

02 componentes do binario.puml  -> png/02 componentes do binario.png
   DIAGRAMA DE COMPONENTES: o binário único (Dockerfile multi-stage) com os
   subcomandos cliente / conversor / storage e as dependências amqp (lapin),
   io_imagem (crate image 0.25) e pasta_entrada/pasta_saida (env).

03 sequencia fanout.puml        -> png/03 sequencia fanout.png
   DIAGRAMA DE SEQUÊNCIA: publica -> entrega (prefetch 1) -> to_luma8 ->
   publica no exchange -> basic_ack -> fanout copia para as duas filas de storage
   -> grava com nome original. Nota final com a prova de redundância.

04 classes dependencias.puml    -> png/04 classes dependencias.png
   DIAGRAMA DE CLASSES (visão macro): app como base e cliente/conversor/storage
   herdando; dependências para lapin, image 0.25 e rabbitmq.

05 classes implementacao.puml   -> png/05 classes implementacao.png
   DIAGRAMA DE CLASSES DE IMPLEMENTAÇÃO (visão de código): classes, campos e
   assinaturas completas prontas para virar Rust.
     main (bin)          -> papel_de(args) / construir(papel, cfg) / main()
     Papel (enum)        -> Cliente | Conversor | Storage
     Config (struct)     -> amqp_url, fila_originais, exchange_convertidas,
                            fila_storage, pasta_entrada, pasta_saida, from_env()
     Servico (trait)     -> executar(&mut self) -> Result<u64>
     Cliente (struct)    -> cfg, canal, publicadas; novo(), executar(),
                            listar_imagens(), publicar(nome, bytes)
     Conversor (struct)  -> cfg, canal, processadas; novo(), executar(),
                            tratar(payload, tag)
     Storage (struct)    -> cfg, canal, salvas; novo(), executar(),
                            salvar(nome, bytes) -> Result<PathBuf>
     Mensagem (struct)   -> nome, bytes; escrever() -> Vec<u8>, ler(payload)
     Topologia (struct)  -> fila_originais, exchange_convertidas, fila_storage;
                            declarar(canal, papel), vincular(canal, fila, exchange)
     modulos             -> amqp (conectar, propriedades_persistentes,
                            prefetch_um), io_imagem (converter, extensao),
                            relatorio, erro
     crates externos     -> lapin::Channel, tokio, image 0.25, anyhow
   Dependências (setas tracejadas) e três notas:
     - ordem do tratar(): converter -> publish -> ack (at-least-once, sobrescreve
       o mesmo nome, não duplica arquivo);
     - declarar() por papel: durable=true, FANOUT, delivery_mode=PERSISTENT,
       ack manual;
     - payload sem dependência nova: 4 bytes big-endian com o tamanho do nome,
       nome UTF-8, bytes da imagem (evita serde/base64).

--- IMPLEMENTAÇÃO (um diagrama por padrão) --------------------------------

06 mapa de modulos por padrao.puml -> png/06 mapa de modulos por padrao.png
   MAPA DE MÓDULOS: o conteúdo de src/ e as arestas de dependência entre os
   padrões. responde "o que importa o quê" antes de existir código. Regra
   visível: a seta nunca volta para a categoria comum; comum nao depende de
   ninguem.

07 factory method.puml          -> png/07 factory method.png
   criacional/factory_method: fn criar(papel, cfg) escolhe a família de
   implementações. FabricaServico (trait) + FabricaReal + FabricaFalsa
   (teste, sem broker). main so conhece Papel e o trait Servico.

08 strategy e template method.puml -> png/08 strategy e template method.png
   comportamento/strategy + template_method: trait Servico com executar()
   NÃO reescrito, e os passos preparar -> (receber -> passo -> confirmar) em
   laço -> resumo, que cada papel sobrescreve. Cliente/Conversor/Storage
   apontam para o mesmo contrato.

09 mediator e command.puml      -> png/09 mediator e command.png
   comportamento/mediator + command: Topologia (declarar/vincular) como ponto
   único dos nomes de fila/exchange; Invocador guarda Box<dyn Servico> e chama
   executar(). Nenhum módulo escreve nome de fila literal.

10 facade e adapter.puml        -> png/10 facade e adapter.png
   estrutural/facade + adapter: Broker esconde lapin (conectar, publicar
   persistente, consumir, ack); io_imagem esconde a crate image
   (converter(bytes) -> Result<Vec<u8>>). As duas fronteiras do projeto:
   trocar broker ou trocar de crate mexe em um arquivo só.

11 decorator e observer.puml    -> png/11 decorator e observer.png
   estrutural/decorator + comportamento/observer: trait Passo com
   tratar(corpo) -> Result<Vec<u8>>, três decoradores genéricos (Validar,
   MedirTempo, Reenviar) + Converter como base; Assunto/Evento/Observador para
   o resumo numérico da execução. O conversor não sabe quantas camadas tem
   por fora.

RENDER — comando usado (plantuml.jar em %LOCALAPPDATA%\Temp\puml):
  cd docs/uml && java -jar "$LOCALAPPDATA/Temp/puml/plantuml.jar" -tpng -charset UTF-8 -o png *.puml

foram testados no render: saem com os sinais < > corretos, não com entidades HTML
nem colchetes.
